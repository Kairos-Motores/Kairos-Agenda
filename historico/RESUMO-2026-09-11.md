## 1. O que é o projeto

- **Kairós Agenda**: app de calendário/workspace corporativo em **React + Vite**, backend **Dataverse** (Microsoft) acessado via proxy serverless (`api/dataverse-proxy.js`, rodando na Vercel).
- Repositório: `Kairos-Motores/Kairos-Agenda`, branch `main`. **Deploy automático na Vercel a cada `git push` no `main`.**
- Raiz do projeto (onde está o `.git`, `package.json`, `vite.config.js`): `calendario/` — não a pasta `Calendario/` um nível acima.
- Módulos principais: Calendário (Agenda), Notas, Tarefas, Visitas (comercial), Painéis BI (Power BI embutido via iframe), SSMA (Saúde/Segurança/Meio Ambiente).

## 3. Como testar localmente (padrão usado a sessão toda)

- Porta de dev: **5199** (não 5173 — o `vite.config.js` de produção não define `server.port`, mas para testar com o preview tool é preciso adicionar `server: { port: 5199, strictPort: true }` temporariamente, senão o Vite sobe em 5173 e a ferramenta de preview procura em 5199 e nunca conecta).
- **NUNCA commitar o `vite.config.js` com mock.** O fluxo é sempre:
  1. Reescrever `vite.config.js` adicionando um plugin Vite inline (`configureServer`) que intercepta `/api/dataverse-proxy` e `/api/bi-embed` com um banco em memória (objeto `db` por tabela, suporta GET com `$filter` simples — `eq`, `and`, `or`, `contains()` — e POST/PATCH/DELETE).
  2. Usar `preview_start` (nome `calendario-dev`, configurado em `.claude/launch.json` na pasta pai `Calendario/`) para abrir o browser embutido.
  3. Login: usar o botão "Ignorar Login (Localhost)" (só aparece em `window.location.hostname === 'localhost'`) ou logar com um usuário seedado no mock (ex: `admin`/`admin`, role `ADMIN`).
  4. Testar a funcionalidade, inclusive dark mode (botão "Ativar modo escuro") e a paleta de accent color (22 cores, no menu lateral).
  5. **Reescrever `vite.config.js` de volta para a versão de produção** (sem o plugin mock, sem `server.port`) antes de build/lint final.
- Exemplo de mock mínimo já usado várias vezes nesta sessão está no histórico do git (procurar nos diffs se precisar reconstruir rápido) — mas nunca ficou commitado, então não tem como puxar de um arquivo salvo.
- **Cuidado com cliques por coordenada no browser tool**: nesta sessão, cliques por `coordinate` erraram o alvo várias vezes (a modal fechava sozinha, ou clicava em outro elemento) especialmente depois que o modal redimensiona. **Prefira sempre `find` + clicar pelo `ref`**, ou `read_page` para pegar o `ref` exato antes de clicar. É mais lento mas muito mais confiável.

## 4. A reforma visual shadcn/ui (pedido original do usuário)

Pedido: "aplique esta paleta de cores, use shadcn para tudo, quero mais refinado, parecido com Android 17 mas mais refinado, divertido, sem tirar as opções de customização do usuário."

### Fundação (não mexer sem entender bem)

- **Tailwind CSS v4** via `@tailwindcss/vite` (sem `postcss.config`, tudo em CSS puro com `@theme inline` em `src/index.css`).
- **shadcn/ui não instalado via CLI** — os componentes em `src/components/ui/` são escritos à mão, usando Radix UI primitives + `class-variance-authority` (cva) + `clsx`/`tailwind-merge` via `cn()` (`src/lib/utils.js`).
- **A ponte crítica**: os tokens shadcn (`--color-primary`, `--color-background` etc., no bloco `@theme inline` de `src/index.css`) apontam para as **mesmas variáveis CSS** que o sistema de tema dinâmico do app já usava (`--text-accent`, `--bg-primary`...), geradas por `applyDynamicTheme` com `@material/material-color-utilities`. Isso é o que garante que os 22 accent colors e o dark mode continuem funcionando em todo componente shadcn **sem precisar tocar em nada dentro de `ui/`**.
- **Armadilha de CSS Cascade Layers**: o reset `* { margin:0; padding:0 }` precisa estar dentro de `@layer base { ... }` em `src/index.css`. Se alguém tirar isso do layer, TODOS os utilitários Tailwind de padding/margin somem silenciosamente (bug real que já aconteceu e foi corrigido).
- **Escala de z-index**: os componentes portados (`Dialog`, `AlertDialog`, `Popover`, `DropdownMenu`, `Select`) usam `z-[12000]`/`z-[12001]`/`z-[12100]` — **de propósito, bem alto**. O app tem chrome fixo próprio com z-index até 5000-9999 (menu lateral = 3100, seu backdrop = 3000, `NavigationSidebar` não usado = 5000) e telas full-bleed legadas que vão até 999999 (`GuidedTour`, `EventDetailModal`). **Se criar um novo componente shadcn com overlay, começe a escala dele em 12000+, nunca no padrão baixo (~2000) que os exemplos de shadcn na internet usam** — já causou um bug real (ver seção 6).

## 5. Feature nova: gestão de permissões de Painéis BI (11/09/2026)

Pedido do usuário: "quero ver facilmente que role/workspace vê qual BI, e quero liberar/proibir BIs por role direto pelo app, só ADMIN."

### O que foi feito

- **`src/config/biConfig.js`** continua sendo a fonte estática de verdade sobre **quais** painéis existem, ícone, descrição, e a qual **workspace** cada um pertence (`workspaceName`) — isso não é editável pelo app, é código.
- **Nova tabela no Dataverse**: `cr4a1_bi_permissaos` (nome de coleção real confirmado via API: `cr4a1_bi_permissaos`). Campos (nomes lógicos reais, **atenção que Dataverse não usa exatamente o que a gente escreve**):
  - `cr4a1_bi_permissaoid` — PK, auto
  - `cr4a1_nome` — texto (nome do painel, só para identificação humana no Dataverse)
  - `cr4a1_biid` — texto, guarda o `id` do painel em `biConfig.js` (**não** `cr4a1_bi_id`, o Dataverse tirou o underscore)
  - `cr4a1_rolespermitidas` — texto, lista de roles separada por vírgula (**não** `cr4a1_roles_permitidas`)
  - Uma linha na tabela = um **override** do `allowedRoles` padrão daquele BI. Painel sem linha = usa o array `allowedRoles` do `biConfig.js` sem alteração.
- **`src/utils/biPermissions.js`** (novo arquivo) — centraliza a lógica de merge entre o padrão estático e o override do Dataverse: `buildBiRolesOverrideMap`, `getEffectiveAllowedRoles`, `hasBiOverride`, `isBiVisibleForRoles`. **Usado tanto pelo `DashboardPanel.jsx` (decide o que cada usuário vê) quanto pelo `UserManagementModal.jsx` (mostra/edita)** — não duplicar essa lógica em outro lugar.
- **`src/hooks/useCalendar.js`**: novo state `biPermissoes` (array cru da tabela), `fetchBiPermissoes` (chamado junto com os outros fetches no load), `upsertBiPermission(biId, biTitle, rolesArray)` (cria ou atualiza a linha de override) e `resetBiPermission(biId)` (apaga a linha, volta ao padrão).
- **`UserManagementModal.jsx`**: nova aba **"Painéis BI"** (só aparece se `isAdmin`), com busca por nome + filtro por workspace + **filtro por role** (responde direto "que BIs essa role vê?"). Cada painel na lista tem um popover de edição (mesmo padrão de Command+checkbox do editor de roles de usuário) com botão "Padrão" para remover o override.
- O editor de roles de cada usuário (aba Membros) também passou a considerar esses overrides na lista "Painéis BI liberados" que já existia.

### Limitação conhecida (avisada ao usuário, não resolvida)

Liberar um BI para uma role nesta tela **não adiciona automaticamente** os usuários daquela role como membros do workspace do BI. Essa sincronização automática (`ROLE_WORKSPACE_MAP` em `src/config/roleWorkspaceMap.js`, usada por `reconcileWorkspacesForRoleChange` em `useCalendar.js`) continua baseada só no `allowedRoles` **estático** do `biConfig.js`, não nos overrides dinâmicos. Se o usuário pedir para "fechar esse gap", é um trabalho futuro — provavelmente dá pra fazer o `ROLE_WORKSPACE_MAP` também considerar os overrides, mas precisa ser recalculado em runtime (hoje é calculado uma vez, no import do módulo, a partir de dados estáticos).

### Como criar tabelas novas no Dataverse (se precisar de novo)

O usuário já autorizou usar as credenciais do `.env` (`DATAVERSE_CLIENT_ID`, `DATAVERSE_CLIENT_SECRET`, `DATAVERSE_TENANT_ID`, `DATAVERSE_ENV_URL`) para criar tabelas/colunas direto via API do Dataverse (Metadata API), sem passar por interface nenhuma. Processo usado:
1. Token: `POST https://login.microsoftonline.com/{TENANT_ID}/oauth2/v2.0/token` com `grant_type=client_credentials`.
2. Criar tabela: `POST {ENV_URL}/api/data/v9.2/EntityDefinitions` com payload `EntityMetadata` incluindo o atributo primário (`IsPrimaryName: true`).
3. Criar colunas extras: `POST {ENV_URL}/api/data/v9.2/EntityDefinitions(LogicalName='...')/Attributes`.
4. Publicar: `POST {ENV_URL}/api/data/v9.2/PublishAllXml` (senão a tabela não fica disponível via Web API/OData imediatamente).
5. **Sempre conferir os nomes lógicos reais depois** (`GET EntityDefinitions(LogicalName='...')/Attributes?$select=LogicalName,SchemaName`) — o Dataverse costuma alterar o `SchemaName` que a gente manda (remove underscores, muda capitalização) ao gerar o `LogicalName` final, que é o que a API realmente usa. **Não assumir, sempre verificar.**
6. Testar CRUD completo (POST/GET com `$filter`/PATCH/DELETE) antes de integrar no app.
7. Rodar o script em Node a partir de **dentro** da pasta `calendario/` (para o `axios` resolver via `node_modules`), com `node --env-file=.env script.js`. **Nunca commitar o script** — é descartável, apagar depois de usar.

## 6. Bugs corrigidos nesta sessão (contexto útil se reaparecerem sintomas parecidos)

1. **Modal renderizando atrás do menu lateral** (`d1b3061`): o `Dialog`/`AlertDialog` do shadcn nasceu com z-index baixo (2000/2001) — mais baixo que o menu lateral (3100). 2. **Painéis BI: faixa invisível no topo bloqueando cliques no relatório** (`452cee4`): o "modo tela cheia" dos BIs tinha uma faixa invisível de 60px no topo só para detectar hover do mouse e reexibir a barra escondida (necessário porque o iframe do Power BI é cross-origin e engole eventos de ponteiro — não dá pra usar `pointer-events: none` nela, senão o hover para de funcionar). 60px cobria a área dos filtros/slicers do Power BI. Reduzido para 14px (só a borda, onde o Power BI nunca põe controle).
